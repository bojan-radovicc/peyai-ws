Scientific Claims Intelligence Pipeline

Back to Projects

A backend-first AI case study on building a production pipeline that transforms raw scientific PDFs into structured knowledge units, verifiable claims, semantic relations, and queryable claim graphs.

Challenge

Scientific evidence is locked in long-form PDFs with inconsistent structure, mixed writing styles, and domain-specific language. Manual extraction is slow, non-repeatable, and difficult to scale.

The core engineering challenge was to make AI extraction reliable under production constraints: multi-step dependencies, LLM latency/timeouts, partial failures, and the need for deterministic, machine-consumable outputs rather than free-form text.

Approach

  • Designed a serverless orchestration workflow where each stage is a dedicated Lambda job (OCR, knowledge units, claims, relations, graph).
  • Standardized intermediate artifacts in DynamoDB to persist stage outputs and make every step idempotent and resumable.
  • Implemented typed LLM extraction with structured schemas to reduce hallucinations and enforce predictable JSON outputs.
  • Added chunk-based processing so document sets can run in controlled batches with bounded runtime per job.
  • Separated semantic phases (units -> claims -> embeddings -> clustering) to improve observability and model tuning.

Architecture & Data Flow

We structured the system as a data pipeline, not a monolithic prompt. Every stage writes durable state, enabling retries, auditability, and downstream analytics.

  • Input PDFs in object storage -> OCR text extraction
  • OCR output -> relevant paragraph filtering -> knowledge unit generation
  • Knowledge units -> typed scientific claim extraction
  • Claims -> embedding + relation clustering -> final claims with relations
  • Final claims -> graph construction -> semantic query endpoint + subgraph retrieval

Technical Decisions & Reasoning

1) Why multi-stage AI instead of one large prompt?

A single prompt over full papers is expensive, hard to debug, and unstable across document types. We decomposed extraction into specialized tasks with typed outputs, which improved reproducibility and made failure handling stage-specific.

2) Why schema-driven extraction?

Portfolio demos often stop at "LLM generated text." We needed production-grade data products. By using typed predictors and domain models, each response is validated before storage, enabling:

  • consistent downstream processing,
  • safer retries and partial reprocessing,
  • clean interfaces between AI and non-AI backend services.

3) How we handled runtime limits and reliability

Lambda runtime and external model latency create real operational risk. We introduced explicit job timeouts, state tracking, and asynchronous invocation chaining. If a chunk fails, workflow state captures error context, increments failure counters, and continues aggregation logic safely.

4) Why graph-based retrieval after claim extraction?

Extracted claims are more valuable when connected. We model claims and relations as a graph so users can query semantically similar nodes and inspect immediate neighborhoods (subgraphs). This turns static extraction into explainable knowledge navigation.

5) Data persistence strategy

We split storage by responsibility: metadata/progress, final claim outputs, graph snapshots, and query results. This separation improves read patterns, keeps operational tables focused, and supports analytics on pipeline quality over time.

Outcome

The result is a production-ready AI data pipeline that converts unstructured research documents into structured, queryable scientific knowledge. Instead of one-off prompt outputs, the system delivers trackable workflow states, reusable intermediate artifacts, and graph-powered retrieval.

Automation Coverage End-to-end

From PDF ingestion to graph query without manual intervention between stages.

Operational Reliability State-driven

Chunk-level progress tracking, timeout guards, and failure accounting for resilient processing.

Processing Performance ~20-30 min

Typical full-workflow completion window for multi-file runs under current batching strategy.

Next Steps

  • Introduce adaptive batch sizing based on document length and OCR complexity.
  • Add automated extraction-quality evaluation (precision/consistency checks on sampled claims).
  • Implement embedding versioning + reindex workflows for safer model upgrades.
  • Add confidence scoring and provenance links from each claim back to source paragraph spans.
