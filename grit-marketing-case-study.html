Grit Marketing Data Platform

A case study of how PeyAI built a reliable ETL platform to centralize ad and lead data, enforce medallion data quality layers, and power repeatable marketing reporting.

Industry Marketing and Lead Generation
Scope Data Ingestion, Transformation, Medallion Modeling, Data Loading, Quality Validation
Tech Stack Python, Click, DuckDB, PostgreSQL, Pandas, Pytest, Poetry, dotenv

Challenge

Marketing performance and lead data were spread across multiple systems, each with different API formats and extraction constraints. Teams needed one trusted pipeline to ingest daily data, standardize schemas, and prepare analytics-ready datasets without manual spreadsheet work or inconsistent business logic.

Approach

  • Implemented source-specific extractors for Google Ads, Facebook Ads, LeadsHook, and LeadsPedia.
  • Built CLI-driven extraction and transformation jobs with configurable date windows and ingestion options.
  • Applied a medallion architecture (bronze, silver, gold) to separate raw, cleaned, and aggregated layers.
  • Used DuckDB for fast in-pipeline processing and PostgreSQL load integration for durable gold outputs.
  • Added test coverage around transformation and loading logic to improve release confidence.

Outcome

The platform established a repeatable, auditable data workflow from source APIs to analytics-ready tables. This reduced manual reconciliation effort, improved data consistency across reporting views, and created a scalable base for future dashboards and decision support.

Architecture & Data Flow

The pipeline is structured around clearly separated processing stages so each step can be tested, re-run, and extended independently. Raw data is never modified after ingestion, and each downstream layer is derived from the previous one through explicit, auditable transformations.

  • Source APIs (Google Ads, Facebook Ads, LeadsHook, LeadsPedia) → Bronze: raw API responses persisted as-is
  • Bronze → Silver: schema standardization, type normalization, deduplication, and null handling
  • Silver → Gold: business aggregations (spend, leads, CPL, conversion rates) ready for reporting
  • Gold → PostgreSQL: final load for dashboards, analytics queries, and downstream consumption
  • CLI orchestration: each stage is a parameterized command supporting date windowing and selective re-runs

Technical Decisions & Reasoning

1) Why DuckDB for in-pipeline processing?

DuckDB allows fast, SQL-driven transformations over local data files without spinning up a separate data warehouse. For this workload — moderate data volumes, batch-oriented — it gives the speed and expressiveness of a columnar engine without operational overhead. The final gold output is then loaded to PostgreSQL for durable, queryable storage.

2) Why CLI-driven jobs over a full orchestration framework?

The pipeline runs on a daily schedule and needs to support manual backfills and selective re-runs without complex infrastructure. A CLI-first design with Click gives teams a predictable, scriptable interface that works locally and in CI environments. Orchestration frameworks can be layered on top when operational complexity justifies them.

3) Why the medallion architecture?

Separating raw, cleaned, and aggregated layers makes failures visible and recoverable. If a business logic change is needed, only the affected downstream layers need to be re-run — raw data stays intact. It also provides a clear audit trail: any gold-layer number can be traced back to its source API response.

Next Steps

  • Add automated data quality checks (row count thresholds, null rate alerts, schema drift detection) between layers.
  • Integrate a lightweight scheduler (Prefect or GitHub Actions cron) for fully automated daily runs with failure notifications.
  • Build a reporting layer on top of gold tables — initially a BI dashboard for CPL, spend, and lead volume trends.
  • Extend to additional sources (TikTok Ads, LinkedIn) using the same extractor interface.
